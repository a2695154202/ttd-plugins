# 微信通知调用示例 · TgtoDrive 插件

**这个插件本身不发消息** —— 它演示的是**一个插件怎么调用另一个插件**：
把内容交给「企业微信通知」插件（`wecom-notify`）发送。

- **插件 id**：`wecom-call-demo`
- **版本**：`1.0.1`
- **入口**：`plugin.py`
- **超时**：120 秒
- **依赖**：标准库 + 容器已装的 `requests`（不可用时自动回退 `urllib`）
- **许可证**：GPL-3.0（与本仓库一致）

---

## 一、结论：其他插件能调用企业微信通知接口吗？

**能。** 判断依据与前提条件如下。

### 判断依据

| # | 依据 | 出处 |
| --- | --- | --- |
| 1 | 运行接口是**普通 OpenAPI 接口**，不是只能由网页调用的私有通道：`POST /api/toolbox/plugins/{plugin_id}/run`「按插件 inputs 定义提交参数，在服务使用的 Python 环境中启动独立进程执行插件。返回后台任务信息，通过任务查询接口读取状态、日志和结果。」并明确「**Bearer 调用无需浏览器的 X-Toolbox-Request 请求头**」 | 接口规范 `spec/tgto-openapi.json`，`documented` 级别 |
| 2 | 插件运行时**被允许调用 OpenAPI**：「BASE_URL 是容器可达的当前服务地址；同一容器通常可使用 `http://127.0.0.1:12366`…使用 requests 时每个请求都设置 timeout，通过 `Authorization: Bearer <TOKEN>` 鉴权，不需要浏览器登录 Cookie。不要导入项目内部模块或直接改数据库来代替公开 API。」 | 官方开发提示词（任务材料 `01-ai-development-prompt.md`） |
| 3 | 鉴权方式统一为全局 `bearerAuth`：`Authorization: Bearer <TOKEN>` | 接口索引 `03-openapi-endpoints.md` |
| 4 | 参数按**目标插件**的 `inputs` 校验：「插件运行接口的 `params` 必须按目标插件 `inputs` 填写，**未知参数会被拒绝**」；且「服务端校验参数类型、未知参数、**选项取值**和数值范围」 | 协议清单 `04-protocol-checklist.md` / 开发指南 `02-plugin-development-guide.md` |
| 5 | 只能调用**别的**插件，**不要递归调用自己**：「避免递归调用自身运行接口」 | 官方开发提示词 |
| 6 | 运行结果通过轮询读取：`GET /api/toolbox/plugins/jobs/{job_id}`「提交运行任务后轮询此接口直到任务结束」 | 接口规范，`inferred` 级别（字段名不保证） |

### 前提条件

| 前提 | 说明 |
| --- | --- |
| 目标插件已安装并**启用** | 未安装时 `run` 返回 404；停用时不会被执行 |
| 持有 OpenAPI 令牌 | 在「实用工具 → OpenAPI」创建，完整值只显示一次；插件从环境变量 `TGTO_OPENAPI_TOKEN` 读取（本示例也允许在表单里填） |
| 已知服务地址 | 环境变量 `TGTO_OPENAPI_BASE_URL`；同容器通常为 `http://127.0.0.1:12366` |
| 参数合规 | 每个键都必须出现在目标插件的 `inputs` 里；`select` 字段的取值必须在该字段的 `options` 内。**否则请求会被判为非法直接拒绝（HTTP 400）** |
| 不要传 `save_settings` | 传 `true` 会把本次调用参数写进**用户**在该插件里的设置；默认 `false`，调用方应保持不传 |
| 目标插件自身已配置好 | 本例中即 `wecom-notify` 的企业 ID / 应用 AgentId / 应用 Secret。**调用方不需要、也不应该持有这些凭据** —— 目标插件会从它自己已保存的设置里补齐 |
| 任务队列有空位 | 「同一插件只能有一个未完成任务；默认最多两个任务同时执行，队列有上限」，满额时提交会失败，需要重试或降级 |
| 遵守 timeout 与结果大小 | 插件 `timeout` 1–86400 秒（默认仅 60）；结果（含运行器包装）**≤1 MiB** |

### 一个必须知道的坑：**「受理」不等于「送达」**

企业微信在**收件人不在应用可见范围**时，**仍然返回 `errcode=0` 与 msgid，只是不投递**。
所以调用方**不能只看传输层的成功状态**，必须读目标插件返回的投递结论：

```python
if result.get("status") == "ok" and result.get("delivery_ok") is not False:
    ok = True                     # 真的送到了
else:
    reason = result.get("delivery_note") or result.get("invalid_users") or result.get("error")
```

本示例插件就是这么做的（见下文「调用链路」第 5 步）。

## 二、界面结构

界面分 **3 个页签**，其中「文本消息」与「卡片消息」是**两个互相独立的子页面**，
各配各的收件人与内容，互不影响；「连接设置」是两者共用的部分。

| 页签 | 字段 | 说明 |
| --- | --- | --- |
| **文本消息** | 收件人、消息正文 | 发纯文本（目标插件 `msgtype=text`）。**收件人默认留空** = 沿用目标插件里已配好的收件人 |
| **卡片消息** | 收件人、卡片标题、卡片内容、点击跳转链接、卡片主图 | 发带图图文（目标插件 `msgtype=news`）。**内容已预填一段示例**，可直接点按钮验证；收件人同样默认留空 |
| **连接设置** | TgtoDrive 地址、OpenAPI 令牌、目标插件 id、等待并校验投递结果 | 共用配置 |

右侧固定两个按钮，就是本示例要演示的两种动作：

| 按钮 | 实际动作 | 目标插件收到的参数 |
| --- | --- | --- |
| **发送文本消息** | `func=send_text` | `{func: "send", envelope: "<JSON 字符串>"}`，envelope 里是 `msgtype=text` + 正文 |
| **发送卡片消息** | `func=send_card` | 同上，envelope 里是 `msgtype=news` + 标题/描述/链接/图片 |

> **为什么只传 `func` + `envelope` 两个键**：发送逻辑全在「企业微信通知」插件里，
> 本插件只负责**准备标准化内容**。这样企业微信侧以后新增能力（新的消息类型、新字段）
> 只需要更新那个插件，**调用方不用跟着改** —— 这正是本次改造的目的。
> 早先版本逐个传 `msgtype` / `touser` / `content` / `title`…，对方每加一个字段，
> 所有调用方都可能要动，是更脆的做法。

> 为什么「卡片消息」走的是 `news` 而不是模板卡片？因为企业微信官方限制下
> **微信插件收不到模板卡片**，而 `news`（大图 + 标题 + 描述 + 点击跳转）微信里能收到，
> 是「卡片效果」在微信可用的实现方式。这也是 `wecom-notify` 只保留 `text` / `news` 的原因。

> ⚠️ **收件人留空的含义**：本插件**不传** `touser`，由「企业微信通知」插件用它自己已保存的收件人。
> 这是推荐用法 —— 你在那个插件里点「发送测试消息」能收到，用的就是那份配置。
> 一旦在这里填了值，就会**覆盖**它；填错成不在「可见范围」里的 UserID，消息就收不到了
> （结果页会提示「已受理，但消息没有投递出去」）。

正文里支持两个占位符，**发送前替换**：`{now}` → 当前时间，`{source}` → 本插件名称。

## 三、调用链路

```text
本插件（wecom-call-demo）
  │
  │ ① 准备「标准化发送内容」（envelope）
  │    {"version":1, "msgtype":"text|news", "content":"…", "source":"微信通知调用示例", …}
  │    只放本次真正需要的键；收件人留空就不放，交回目标插件用它自己的配置
  │
  │ ② 读目标插件清单（前提校验，不发请求）
  │    GET  /api/toolbox/plugins                        Authorization: Bearer <TOKEN>
  │    · 目标插件在不在、启没启用？
  │    · 它是否支持 envelope？（不支持就提示去更新它）
  │    · 本次要传的键是否都已声明？
  │
  │ ③ 提交运行任务（只传 func + envelope）
  │    POST /api/toolbox/plugins/wecom-notify/run
  │    body: {"params": {"func": "send", "envelope": "<JSON>"}}   ← 不传 save_settings
  │    ← 202 + 任务信息（字段名不保证，任务 ID 容错提取）
  │
  │ ④ 轮询结果
  │    GET  /api/toolbox/plugins/jobs/<job_id>
  │    ← 状态兼容 status / state；任务对象可能在 result / job / data 任一层
  │
  │ ⑤ 区分「受理」与「送达」
  │    ← 读 delivery_ok / recipient / invalid_users / delivery_note / envelope_source
  │      delivery_ok=false ⇒ 报告「已受理，但消息没有投递出去」并给出处理办法
  │      envelope_source  ⇒ 确认「我传的内容被用上了」
  │
  ▼
wecom-notify：在自己的进程里加载自己的配置（企业 ID / Secret / 收件人），按 envelope 组装并发送
```

第 ① ② 步是本示例的重点：**先把内容标准化，再把服务端会拒绝的参数挡下来**。
这样遇到问题时看到的是「参数 X 不在目标插件的选项内」或「目标插件不支持 envelope」，
而不是一句难懂的 `HTTP 400`。

### 调用方要做的事，就这三件

1. **准备标准化内容**（一个 dict）：
   `{"version":1, "msgtype":"text|news", "content":"…", "items":[["键","值"]], "title":"…", "url":"…", "image":"…", "source":"我的插件"}`
2. **调运行接口**：`POST /api/toolbox/plugins/<目标插件>/run`，
   body 为 `{"params": {"func": "send", "envelope": json.dumps(env, ensure_ascii=False)}}`；
   拿到 **HTTP 202 + `job_id`** 就说明已被接受。
3. **（可选）确认投递**：轮询 `GET /api/toolbox/plugins/jobs/<job_id>`，读 `delivery_ok` / `recipient`；
   `delivery_ok=false` 表示「被企业微信受理了但没送到」。

**发送逻辑（凭据加载、企业微信请求体、分段、投递校验）一行都不用写** —— 全在「企业微信通知」插件里。
本插件的 `plugin.py` 就是这三件事的完整参考实现（含前提校验、任务 ID 容错提取、投递判定），
需要照抄时直接读它即可。字段表见
`wecom-notify/CALLING.md` §三「标准化发送内容」。

### 这条路是受支持的调用方式

不必怀疑「插件只有从界面点按钮才会执行」：运行接口的用途就是
「**按插件 `inputs` 提交参数 → 启动独立进程执行插件**」，它在 OpenAPI 里以 `bearerAuth` 暴露，
且明确「Bearer 调用无需浏览器的 X-Toolbox-Request 请求头」；唯一相关的禁令是
「避免递归调用**自身**运行接口」，**调用别的**插件没有限制。

**判断「是否被接受」只看首个响应**：

| 你收到 | 含义 |
| --- | --- |
| **HTTP 202 + `job_id`** | 触发已被接受、目标插件已在执行（本示例就是靠这个继续轮询结果的） |
| HTTP 404 | 目标插件未安装 / 未启用（或 id 写错） |
| HTTP 400 | 参数被拒（本示例的预校验会提前拦住，并列出是哪个键 / 哪个取值） |
| HTTP 401 / 403 | 令牌无效或权限不足 |
| HTTP 503 | 队列已满，或目标插件已有未完成任务 |

## 五、如何新增一种通知（扩展点）

以「新增一个『发送告警』按钮，走另一个通知插件」为例，三步：

1. **清单**（`plugin.json`）：在 `func` 的 `options` 里加一项，例如
   `{"label": "发送告警", "value": "send_alert"}`；需要的新输入也在这里声明，并放进 `ui`。
2. **映射表**（`plugin.py` 的 `ACTION_SPEC`）：加一行，指明它用哪个页面的收件人/内容字段、
   以及发给目标插件的 `msgtype`。
3. **处理方法**：仿照 `_send_text()` 写一个 `_send_alert()`，装配好参数后调用
   `self._send(spec, params, touser)` —— 前提校验、提交、轮询、投递判定都由 `_send()` 统一处理，
   不需要重复实现。最后在 `execute()` 的 `handlers` 字典里登记。

如果只是想换一个通知出口：把「目标插件 id」改成那个插件的 id 即可（前提是它同样接受
「收件人 + 内容」这套输入）。

## 六、排错

| 现象 | 原因与处理 |
| --- | --- |
| 结果页显示「**未发送：目标插件的调用前提不满足**」 | 预校验拦下的问题会逐条列出（键未声明 / 取值不在选项内 / 未启用 / 缺必填项），照提示改即可 |
| 「未配置 OpenAPI 令牌」 | 填「连接设置 → OpenAPI 令牌」，或配置环境变量 `TGTO_OPENAPI_TOKEN` 后重启服务 |
| HTTP 404 | 目标插件未安装或未启用（或「目标插件 id」填错） |
| HTTP 401 / 403 | 令牌无效或权限不足 |
| HTTP 503 | 服务暂时不可用，或目标插件已有未完成的任务（插件队列满） |
| 「**已受理，但消息没有投递出去**」 | 企业微信收下了请求但在可见范围上拦住了。到管理后台该应用的「可见范围」加入收件人，或把收件人改成正确的 UserID |
| **在「企业微信通知」里点测试能收到，用本插件发却收不到** | 先看两个子页面的「收件人」**是否填了值** —— 填了就会**覆盖**目标插件里已配好的收件人。把它清空（留空 = 沿用目标插件设置）再发一次。结果页的「实际收件人」会直接告诉你这次发给了谁，可与目标插件自己的测试对照 |
| 「发送成功」但手机没收到 | 说明企业微信确认收件人在范围内，问题在微信侧：检查是否关注了「微信插件」、是否勾选了「在微工作台中始终进入主页」（勾选后微信端只能收到文本）、微信插件的「接收应用消息」开关。详见 `wecom-notify` 的 README「七、在微信中接收消息」 |
| 目标插件任务里报 `60020` | 调用 IP 不在该应用的「企业可信IP」名单 —— 这与本插件无关，是「企业微信通知」的出口 IP 问题：在它的「① 应用凭据 → 代理地址」填好转发代理**并保存**，或到企业微信后台加白名单。保存的代理地址经本插件调用同样生效（错误文案里的「本次请求实际发往」会说明代理有没有被用上） |

## 七、安装与使用

### 手动导入

导入**打包产物**，不要导入源码目录里的 `plugin.py`：

| 文件 | 说明 |
| --- | --- |
| `wecom-call-demo.py`（单文件，推荐） | `dist/` 下生成，包含内联清单 |
| `wecom-call-demo.zip`（插件包） | 内含 `plugin.json` + `plugin.py` + `README.md` |

> ⚠️ `plugins/wecom-call-demo/plugin.py` 是插件包内的入口，清单在同目录 `plugin.json` 里，
> 单独导入会报「Python 单文件必须在顶层定义唯一的 PLUGIN_MANIFEST 常量字典」。

### 使用步骤

1. 确认「企业微信通知」（`wecom-notify`）已安装、启用并配好企业 ID / AgentId / Secret；
2. 打开本插件，在「连接设置」填 OpenAPI 令牌（或配好环境变量）；
3. 切到「**卡片消息**」页，内容已预填示例 → 点右侧「**发送卡片消息**」；
4. 在结果页核对：**实际收件人**、**投递校验结论**、以及「实际发出的参数」。

### 本地构建

```bash
python scripts/package_plugin.py --plugin wecom-call-demo
```

## 九、协议与实现说明

- 同步 `run(params, context)`；**模块导入阶段不发任何请求**，全部网络调用都在 `run` 内；
- 每次请求都设 `timeout`，`allow_redirects=False`，并检查状态码；不把 `Authorization` 转发到外部 URL；
- 令牌、`corp_secret` 等凭据不会出现在运行日志、结果页与返回值中（结果里回显的目标插件响应会经 `scrub_text()` 处理）；
- 只写 `context["data_dir"]`（本示例实际不写文件），不触碰 `plugin_dir`；
- 该接口在规范里标注 `inferred`（无响应 schema），因此任务 ID、任务状态、插件条目字段名都做**容错读取**，
  取不到时会把响应片段写进日志，避免「提交成功但查不到原因」。
